# PRD — the in-process interview

Continuation of `project-manager` §4 for `PRD` (aliases `ПР`, `ТЗ`): the installed `product-technologist` skill runs in this process, interviews the human, and hands back the document and the title; you persist them through the adapter, collect the session's usage, and stop — a ready PRD moves no stage.

## Target and workspace

- Target: the invoked key itself — resolved by the §3 call with `"self": true`, `"attachments": true`, `"parent": true`, `"mark": true`. A parent key stays the target even with unfinished children. An explicitly invoked child is a first-class target (an epic-style child is a full task): the document lands in the child, its parent is neutral context, and no stage moves anywhere. `PRD` without a key (and without a key-shaped current branch) targets a new item created after the interview (`routes/create.md`).
- Workspace: the primary checkout as it stands — the interview and its research run in the project root the dispatcher's bootstrap found, on whatever branch it holds; the run's only persistence is the tracker document. Branch, worktree, and commit are development vocabulary (§5).

## Materials

- The §3 resolution is the tracker material: `files.issue`, `files.parent_issue` for a child, `files.comments`, and the downloaded visuals under `media[].path` — the skill reads every supported visual once so it stays in context for the whole interview. An unreadable material visual is a question for the human, never a stop.
- The baseline: an existing managed document (`document.managed`) is the settled part of the design tree — the interview covers only its gaps and what the human wants changed, and the write replaces the whole managed block. A legacy document (`document.legacy`) and any human-written description are plain item text: material for «Проблематика», removed on write only inside the managed block and otherwise moved below the separator. A submitted plan (`routes/create.md`) is settled material too.
- Another item's text during the interview comes from one more read-only `resolve` call (`"self": true`, no `mark`). Until the skill hands off, nothing is written to any description, stage, or comment.

## Brief and invocation

1. Right before invoking the skill, state the brief in one short chat block — the target (`<KEY> — <title>`, or «новая задача» / «подзадача под <PARENT_KEY>», `routes/create.md`, plus the creation fields the manifest's `create_fields` names, which the interview collects in its first round), the item material as `@<path>` links — `@<files.issue>`, `@<files.parent_issue>` for a child, `@<files.comments>`, every `media[].path` — which the skill reads itself, the user's words beside the token as boundaries and decisions, whether a document already exists (`document.managed` / `document.legacy` / none), the size (XS–XXL) when the user's words name one, else the resolution's `target.size` — neither: the item is left out and the skill computes it from its research, the repository root (the bootstrap's `repo.toplevel`, or «репозитория нет»), the project's terminology document as one more `@<path>` link when the bootstrap reports it (`references.terminology`; `null` — left out; the skill reads it, you never open it; `references_missing` adds one chat line `Предупреждение: терминология не найдена — проверьте references.terminology в dreamteam.json` and the run goes on), the mockups directory (`<run_dir>/mockups` — where the interview keeps its mockup files when the runtime has no visualization directory of its own), and the research launch profile: the bootstrap `models.research_ultra` row when the command carries `ультра`, else `models.research_<size>` for the size just named in the brief, else `models.research` (size not settled) — the row stays as briefed even if the skill computes another size — the skill's read-only research children launch through the runtime's subagent launcher with that model and effort out-of-band, the way §6.3 launches a role, without any DreamTeam skill selection. No Assignment v1: in-process there is nothing to sanitize.
2. Invoke the installed `product-technologist` skill in this process — Claude Code: the Skill tool (`dream-team:product-technologist`); Codex: read `<roles.root>/skills/product-technologist/SKILL.md` and follow it. Then follow the skill to the letter: its rounds, its research, its stop tokens. The interview is exempt from the §13 narration cap end to end, and every human answer is a continuation of this run (continuation discipline). During the interview the tracker is read-only — `resolve` without `mark` — and nothing is written before the skill hands off.
3. The skill ends with one fenced `markdown` block, one `Заголовок:` line, and one `Макеты:` line — absolute paths separated by `; `, or `нет`. Take all three verbatim; write nothing of your own into any of them.
4. Confirmation gate — nothing is written to the tracker before the human confirms this text. Post the handoff document verbatim as one fenced `markdown` block in chat, with the `Заголовок:` line beside it and one `Размерность: <XS–XXL>` line — the working size the interview ended on: the size the skill last stated and the human did not change, which is the brief's size when it never named another; never your own estimate; a run where none was stated has no such line and writes no size — and ask «пишу в трекер?». A size the human names at the gate replaces it. The run waits for their word: corrections go back to the skill in-context and its corrected document replaces the handoff, which is shown again the same way; a refusal ends the run with no write at all (Run model), the document staying in chat. Only an explicit confirmation opens Persistence — mockup attachments included.

## Persistence

1. Mockups — when the `Макеты:` line lists files: render them with one call `node "<scripts.mockup_render>" '{"files":["<path>",…],"outDir":"<run_dir>/mockups"}'` (a `null` script path means the installed DreamTeam predates the renderer: every listed file is its own output), then attach every output with one call `attach '{"key":"<KEY>","files":["<output>",…],"replace":true}'` — a same-name attachment on the item is replaced. A `failed` render item attaches its `source` instead and adds one chat line `Предупреждение: макет <name> не отрисован — <code>`; an item with `attached: false` adds `Предупреждение: макет <name> не вложен — <code>`; neither stops the run. Reference gate before the write: every `🖼️ Макет: <file>` line of the document names an attached file (by name, or by stem when a source was attached in place of a render); an unmatched name goes back to the skill in-context once, with the attached names, and its corrected document replaces the handoff — a second mismatch is one chat warning, and the write proceeds.
2. Existing target: write the fenced Markdown to `<run_dir>/prd.md` and invoke the writer once: `prd '{"key":"<KEY>","document":"<run_dir>/prd.md","title":"<Заголовок>"|null,"size":"<XS–XXL>"|null}'` — `title` null when the line is `Заголовок: без изменений`; `size` is the size the gate named, null when none. The adapter validates the canon (both `#` blocks — the `##` spelling is accepted — the four required `##` subsections — the `###` spelling is accepted — the closed optional set), removes every managed and legacy section — a legacy block included, reported in `legacy_removed` — lands the block in canonical order at the top of the description, preserves every byte outside it below the separator, writes the title and the size in the same update, and proves the write by a re-read. `malformed_sections` → hand its `problems` list to the skill in-context verbatim, take the corrected document, retry the write exactly once; a second rejection is a §12 stop. Any other `ok: false` — an `invalid_size` included — is a §12 stop; a size the tracker refuses is reported in one chat line. Never compose or patch the description yourself.
3. New item: `routes/create.md` creates it with the title, then the mockups step and the same `prd` call (`title` null — the name already is the title) land the attachments and the document.
4. Time, when the manifest declares it: one call `time '{"key":"<KEY>","stage":"prd","runtime":"codex"|"claude","session_id":"<§6.4.2 session id>","root_agent_ref":null}'` — whole-session scope, the session itself is the root; the §6.4.5 warning lines apply unchanged.
5. Usage — «Затрачено»: run the shared DreamTeam collector once in whole-session scope: `node "<scripts.agent_usage>" '{"runtime":"codex"|"claude","sessionId":"<§6.4.2 session id>","label":"PRD"}'` — no `rootAgentRef`: the session itself is the root, its research children included. No session id → skip it and emit `Предупреждение: метрики PRD не собраны — session_id_unavailable.`; a `null` script path is `collector_unavailable`. `ok: true` → publish `comment_html` verbatim through one `comment` call with `"required": false` (best-effort, §6.4.4) and keep `rendered.block` for the report; `ok: false` → its `warning_line` as one chat line. Copy every string verbatim. A repeat PRD in the same session records the session again — best-effort observability; a fresh session per PRD keeps the numbers clean.
6. Stop (Run model). No stage move — the human moves it after validation. The §13 report names the persisted sections (`inserted`/`replaced`), `legacy_removed` when non-empty, the title outcome, the size outcome (`replaced` as «размерность <value>», `unchanged` as the standing value; `none` — one chat line), «stage не менялся», and the «Затрачено» block. A document carrying «Рекомендация по разбивке» ends the report with `<KEY> разбей` as the next command (`routes/split.md`); on a child target the recommendation stays a chat line — `разбей` applies to parent/ordinary items only (nested children are unsupported). No Development Follow-up block.
