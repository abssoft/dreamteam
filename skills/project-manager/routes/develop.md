# Development Modes — разработка, QA, Ревью, подряд

The human command has priority. Development uses best-available material: the persisted PRD when present (`document.managed`), otherwise the selected item text — a legacy document (`document.legacy`) counts as none. A missing product document or Scope is input to compensate for, never a gate.

## Entries and children

- `разработка` → Development → QA → Review, with at most `policy.returns` returns to Development (a red QA gate, a failed branch migration before QA and Review fixes counted together); the next return stops `needs_human`.
- `Ревью` → completion recovery first; otherwise QA and then review of the existing task branch. A parent whose direct children are all finished is reviewed the same way over its whole branch against `policy.base`, without a `development_result` — its work lives in the subtasks' Results, which are not stand-ins for one. Recovery with marker `review_done` follows `routes/deliver.md` without relaunching completed work.
- `разработка просто` (`easy`, `легко`; legacy `быстро`, `изи`, `тривиально`, `trivial`) → load `routes/easy.md`. `просто` is a modifier, never a command by itself.
- `подряд` (`все`) → every unfinished direct child sequentially, stopping on the first blocker.

For a child, resolve with `"parent": true`; its own text is primary and the parent description plus `Подзадача N из M` are neutral source material. Parent markers never control it. One child per ordinary invocation; no nested-child recursion.

The AI mark is already applied by the §3 resolution call (`"mark": true`). A Development entry publishes `dev_started` before the launch (one `publish` call without a comment) and never moves a later stage backward. A Review entry requires an existing canonical branch; completion markers route through recovery instead of relaunching completed work.

## Assignment composition

One call composes, validates and writes every packet — never a hand-written JSON: `node "<scripts.assignment>" '{"runDir":"<run_dir>","mode":"develop"|"review","key":"<KEY>","title":"<exact item title>","baseRef":"<base>","validator":"<scripts.validate_assignment>","files":{"issue":"<files.issue from the resolution>","parentIssue":"<files.parent_issue, child runs>","mockups":["<media[].path of every image>"]},"position":"<children.position, child runs>", …mode fields}'`. It returns `path` — the packet file the launch names (§6.3) — and `assignment_id`; `ok: false` with `invalid_packet` names every problem: fix the inputs and call again, a launch never follows a failed call. You read no item text: the PRD, the original request, the parent and the mockups reach the role as files, and the role treats the managed PRD block of `issue` as the accepted product decision with its «Критерии приемки» and `## Scope`.

- `baseRef` = the base §5 fixes: `policy.base` for an ordinary/parent item, the parent key for a child — a name, never a sha and never a path. One exception: a repeat Review passes the `reviewed_head` of the previous Review launch (§5.7), a revision rather than a name, so the reviewer reads the fix delta and carries its previous coverage over instead of judging the whole change again.
- Development (`mode: "develop"`, launch row `developer_<size>`, or `developer_ultra` under `ультра` — the row rule of §6.3, the same row for every attempt; name the size in the run's chat line): `verification` = the dispatcher's own checks beyond the PRD, real commands only, when the brief names any. Under the modifier `гейт` every Development packet of the command adds `declareGate: true` (§4). With a stage (§5.8), `environmentText` = the `environment_text` of the stage preparation right before this launch, and after a failed branch migration `migrationErrorPath` = its `migrations.error_path` — the developer applies no migrations: QA checks the schema on a stage that already has them. On a re-entry — the item's first prepare-worktree call of this command returned `prepared.prior_commits` above 0: the task branch already carried work from an earlier run or a delivery (§5.7; a repeated command in the same session takes its own first call and, as an exception to the continuation rule, a fresh resolution, so the comments written since are in the file) — every Development packet of the command adds `feedbackPath` = `files.comments` of the resolution: the tracker comments ride as the `feedback` material, evidence of what did not work rather than an instruction or scope, and you still read none of them. A fixes retry adds `reviewPath` — the reviewer's Result file (`deliverable.content.path` of its envelope): it rides as the `review` material with the fixes and their evidence and marks the retry, and the script carries the reviewer's `required_fixes` into the packet verbatim. A return after a red QA gate adds `qaResultPath` — the QA result file: the script composes `required_fixes` (`Q<n>` lines, one per failed item) from it and rides the file as `qa_result`, and refuses a file whose `verdict` is not `red` with `qa_not_red`.
- Review (`mode: "review"`, launch row `reviewer_depth_<level>`, or `reviewer_ultra` under `ультра`): `developmentResultPath` (omit it when no Development ran in this item — the parent-after-children case) — the developer's Result file (`deliverable.content.path` of its envelope), riding as the `development_result` material — and `qaResultPath` — the QA result file of this change, riding as `qa_result` (DreamTeam's contract rejects a review packet without it); the script reads the file, refuses a `red` verdict with `qa_red`, and returns `qa: {verdict, obstacles, executor_broken}` beside `path`. A repeat Review after a fixes cycle adds `reviewPath` — the previous review's Result file, riding as `previous_review` — and takes its `baseRef` from that `reviewed_head`. Then gate the base and the diff in the prepared workspace: `node "<scripts.review_pack>" --assignment "<path>" --check`; `ok: false` → fix and re-run, a launch never follows a failed check; `review_state_mismatch` is never fixed by a bare re-run — QA evidence for another HEAD → run QA again on this HEAD (no return counted) and route its gate anew, uncommitted changes in the review workspace → §12 branch or workspace mismatch stop, the tree untouched. `ok: true` carries `depth: {level, reason}` — the review depth the change's most expensive hunk buys (1 documentation/generated/tests only … 5 irreversible data work or two risk categories; one lower on a repeat review): launch with the bootstrap `spawn_args.reviewer_depth_<level>` (`spawn_args.reviewer_ultra` under `ультра`) and name the level with its reason and the workspace HEAD as `reviewed_head` in the run's chat line; a subtask or fast-path gets no correction of its own. With no PRD block the role derives obligations and verification from the item text and the diff.

## Development translation

Commit accepted scoped changes through one `deliver.mjs` call before publication: `{"mode":"commit","workspace":"<prepared workspace>","key":"<KEY>","base":"<policy.base>","resultPath":"<deliverable.content.path of the envelope>","subject":"<KEY> <exact title>"}` — the script stages the Result's `changed_paths` and composes the body (`## Что сделано` from the deliverable, `## Почему` from its `why`, `## Проверено` from the verification items); you retype nothing. A fixes commit uses subject `<KEY> правки ревью <cycle>`. Any mismatch or failed commit stops before any tracker mutation.

Then write the fixed short completion comment to `<run_dir>/comment.md` — first line to last, nothing else:

```text
Разработка: готово
Блокеров: нет
```

`Блокеров: нет` is literal — an accepted `done` is the only path here. The full report (concrete changes, root cause, verification evidence) stays in the accepted Result and the commit body above; the comment never carries it. Record time when the manifest declares it (§6.4.5, stage `developer`), then publish with one call `publish '{"key":"<KEY>","event":"development_done","comment":"<run_dir>/comment.md"}'` — the adapter posts the comment and moves the stage to `review`. Then run QA.

## QA — the in-process gate

The project's whole mechanical gate — linters, static analysis, type checks, builds, tests — runs once here, between the accepted Development commit and Review, by the installed `qa-engineer` skill in this process on the session model: no launch, no `models` row, no Assignment, no Result v1. The developer ran at most its own tests; the reviewer runs nothing and reads the QA result. The gate is exactly the `checks` list of the workspace's `dreamteam.json` — nothing is derived from the project's scripts or added from its rules; an item the profile declares with a baseline policy settles itself from its log inside the QA script, and an item the profile binds to `paths` runs over the files of the change it names (or is not run when the change misses them) — a return runs the same narrowed gate, never a wider one.

0. With a stage, prepare it first (§5.8) — after the Development commit, and on the `Ревью` entry before its first QA. `migration_failed_branch` here is a return to Development instead of QA: a new `software-developer` Assignment with `migrationErrorPath` (and the fresh `environmentText`), counted toward the returns; commit its accepted fix with subject `<KEY> правки миграции <n>`, then prepare the stage and run QA.
1. Brief, one short chat block right before the invocation: the workspace (the prepared workspace path — in-process, so it is stated here and never in a packet), the base ref (`policy.base` for an ordinary/parent item, the parent key for a child — QA always judges the whole change, a repeat after a return too), the run directory for its files, an id `<KEY>-qa<n>` (n counts the QA runs of this session), the stage's two `qa_brief` lines verbatim when a stage runs (the environment line and the owner's permission for browser checks on the stage), and the dispatcher's own check commands when the brief names any, as real commands. The gate itself is not in the brief: the role takes it from `checks` of the workspace's `dreamteam.json` (§1.5), and no tool is added for a language or a stack.
2. Invoke the installed `qa-engineer` skill in this process — Claude Code: the Skill tool (`dream-team:qa-engineer`); Codex: read `<roles.root>/skills/qa-engineer/SKILL.md` and follow it. The skill ends with one fenced item list, one line `Гейт: green` | `Гейт: red` | `Гейт: unconfirmed`, and one line `Результат: <absolute path>`; a run that ends otherwise is a malformed handoff → §12 stop, workspace preserved.
3. Route on the `Гейт:` line. The line is the chat trail; `assignment.mjs` checks the decision against the `verdict` field of the `Результат:` file — `qa_not_red` on a return packet, `qa_red` on a review packet, `qa_result_invalid` on a file that is not a QA result: a discrepancy is a malformed handoff → §12 stop, workspace preserved, never a second call in the other mode. A review packet also refuses a result whose gate did not come from the workspace's `checks` — `qa_gate_undeclared`: the workspace's `dreamteam.json` declares none (the primary's copy is uncommitted or unpushed, or the developer under `гейт` left it out) → §12 stop naming that file, workspace preserved. `red` → a return to Development: compose a new `software-developer` Assignment per the composition above with `qaResultPath` = the `Результат:` path (it counts toward the return limit shared with Review fixes), commit the accepted fix with subject `<KEY> правки QA <n>`, publish nothing, then run QA again. `green` or `unconfirmed` → check the stage (§5.8: `state`, not running → stop `stage_unhealthy`), then dispatch Review with `qaResultPath` on the review packet. Nothing is published to the tracker for QA itself: the Review comment carries the surviving `SKIP`/`BROKEN` items, and on `unconfirmed` the §13 report states «гейт не подтверждён: <`qa.obstacles` of the review packet call>» so the delivery decision stays with the human.
4. QA is part of your own session, not a launch: no metrics collector call and no time record for it; the host row of the terminal «Затрачено» table covers it. Copy the fenced item list into chat as it came — it is the run's trail.

## Review translation

Non-empty `required_fixes` publishes no completion marker and moves no stage: record time when declared, dispatch a new Development Assignment as above, and carry the accepted fix through the rest of the pipeline in the same turn: commit → QA → the next Review. At most `policy.returns` returns to Development per run, red QA gates, failed branch migrations before QA and Review fixes counted together. Empty fixes with accepted evidence requires a clean committed workspace (a fresh prepare-worktree snapshot proves it; leftovers postdate the Development commit → blocker, no stage move), then the comment file:

```text
Ревью: готово
Блокеров: нет
<optional line: every surviving SKIP/BROKEN verification item>
```

The optional third line renders every surviving `SKIP`/`BROKEN` listed as `<QA-пункт> — SKIP | BROKEN`, joined with `; `; omit the line when none survive. Record time when declared (stage `reviewer`), then publish with `publish '{"key":"<KEY>","event":"review_done","comment":"<run_dir>/comment.md"}'`.

An ordinary/parent item is moved to `done` by the adapter's `review_done` and performs the selected close-out (§11). A child publishes the marker, stays in `review` until its automatic local merge succeeds, then `close` finalizes it. `подряд` reloads the parent after each closed child and repeats with fresh Assignments; a child whose last review packet returned `qa.executor_broken: true` is still carried through its merge and `close`, and, while unfinished children remain, the next one is not started — stop `gate_environment_broken` (§11). It never runs `PRD` or delivers the parent.
